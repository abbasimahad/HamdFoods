# Administration Settings — Design

**Date:** 2026-09-14
**Baseline:** `9f585f652725d3542b40010a25314578f651d95e` (`main`, HEAD == origin/main, Purchase Invoices COMPLETE)
**Status:** DESIGN ONLY — not implemented. Requires explicit approval before schema/migration/code work begins.
**Route:** `/administration/settings` (currently `planned`/`MISSING` — the sole remaining `MISSING` workflow)

This document is derived from a full inspection of the current configuration/settings surface: `/accounting/settings`, user/role administration, the audit log, account security, all master-data pages, numbering sequences, print/branding surfaces, and the deployment/runtime scripts. Source and current code win over any prior assumption about what this route should contain.

## RECOMMENDED ADMIN SETTINGS

**Exactly one genuine surface qualifies: Company / Factory Profile.** No other candidate survived inspection without either already having an owner, requiring a feature that doesn't exist yet, or being explicitly out of bounds for a web setting.

### Company / Factory Profile

| Field               | Purpose                                                            | Type      | Default                                                                                  | Validation                                                                                                                              |
| ------------------- | ------------------------------------------------------------------ | --------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `legalName`         | Printed-document header, in-app branding fallback                  | `String`  | `"Hamd Foods ERP"` (matches current hardcoded value, so nothing changes on first deploy) | required, trimmed, 1–200 chars                                                                                                          |
| `address`           | Printed-document header (supplier/customer-facing legitimacy)      | `String?` | `null`                                                                                   | optional, trimmed, ≤500 chars                                                                                                           |
| `city`              | Printed-document header                                            | `String?` | `null`                                                                                   | optional, trimmed, ≤120 chars                                                                                                           |
| `phone`             | Printed-document header, contact                                   | `String?` | `null`                                                                                   | optional, trimmed, ≤40 chars                                                                                                            |
| `email`             | Printed-document header, contact                                   | `String?` | `null`                                                                                   | optional, trimmed, valid email format if present, ≤200 chars                                                                            |
| `taxRegistrationNo` | Printed-document header (supplier/customer compliance expectation) | `String?` | `null`                                                                                   | optional, trimmed, ≤60 chars — same shape as the existing `Supplier.taxRegistrationNo`/`Customer` equivalent, not reusing their storage |

- **Persistence model:** one singleton row, `id: "default"`, reusing the exact established convention already proven by `AccountingSettings { id String @id @default("default") }`. No new persistence pattern is introduced.
- **Permission:** a new `settings.manage` permission code gates the entire `/administration/settings` page (view + edit together), mirroring how `/accounting/settings` gates its whole page on `accounting.manage` rather than splitting view/edit. Default role mapping: `SUPER_ADMIN` and `ADMIN` only (both already receive the full `PERMISSIONS` set in `DEFAULT_ROLE_PERMISSIONS`; no other default role gains anything new). The company name/address are not secret, but changing them is a controlled, auditable action, so no separate unauthenticated or broad-view path is added.
- **Audit requirement:** every save writes one `AuditEvent` (`action: "UPDATE"`, a new `entityType: "COMPANY_PROFILE"`, `beforeSnapshot`/`afterSnapshot` of the changed fields), exactly matching the pattern already used by `updateAccountMappingAction`. No field is sensitive enough to need scrubbing, but the existing `recordAuditEvent()` scrubber applies uniformly regardless.
- **Future-only vs. historical:** this setting affects **presentation only** — printed documents and in-app branding always render the _current_ profile at view/print time, identical to how `Supplier.address`/`Customer.address` are already read live from the master-data relation on every print page today (confirmed: `prisma-purchasing-repository.ts` reads `row.supplier.address` fresh on every `getPurchaseOrder()` call, not a value frozen at document creation). No PO/invoice/payment amount, status, date, or posted accounting/inventory fact is touched. Historical transactional records remain byte-for-byte unchanged; only their printed header text reflects the latest saved profile, which is the same behavior already accepted for supplier/customer identity today.
- **Scope boundary (explicit):** V1 is text fields only. No logo/image upload — this codebase has no file-upload/storage capability anywhere today (no product photos, no avatars, no attachments), and adding one is disproportionate to "print the company name." The PWA manifest (`manifest.ts`) and the root `<html>` `<title>`/`metadata` (`layout.tsx`) stay build-time constants and are **not** wired to this setting in V1 — making the root layout dynamic would add a database read to every single page load including the pre-authentication login page, which is a real performance/complexity cost for a rarely-changed value; only the already-per-request-rendered print pages and the authenticated shell header (`top-header.tsx`, already server-rendered per request behind auth) read the new setting.

No other setting is recommended. Building anything beyond this one profile would be inventing configuration the codebase doesn't currently need, which this task explicitly says not to do.

## KEEP / REMOVE ROUTE

**KEEP**, scoped narrowly to the Company / Factory Profile above. The route is not being removed, because a genuine, evidenced, currently-unowned gap exists (hardcoded company identity absent from every printed commercial document) — but it is also not being filled with invented settings merely to justify the route's existence. If the operator would rather leave the hardcoded string as-is indefinitely, the alternative is explicitly: **REMOVE** the planned sidebar entry and close this as "no legitimate general settings remain" (see Decisions).

## SCHEMA NEEDED

```prisma
model CompanyProfile {
  id                String   @id @default("default")
  legalName         String
  address           String?
  city              String?
  phone             String?
  email             String?
  taxRegistrationNo String?
  updatedByUserId   String?
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt
  updatedBy         User?    @relation("CompanyProfileUpdatedBy", fields: [updatedByUserId], references: [id], onDelete: Restrict)

  @@map("company_profile")
}
```

- New `PermissionCode` value: `"settings.manage"`.
- New `AuditEntityType` value: `"COMPANY_PROFILE"`.
- One additive migration: `CREATE TABLE company_profile`, seed exactly one `id: "default"` row at `legalName: "Hamd Foods ERP"` (matching current behavior with zero visible change on deploy), `ALTER TYPE "AuditEntityType" ADD VALUE 'COMPANY_PROFILE'`. No existing table, column, or trigger is touched — same additive discipline as the Purchase Invoices migration.
- No new database guard trigger is required: this is a single-row, non-posted, non-financial, non-inventory record with no lifecycle (no DRAFT/POSTED/REVERSED states) and no downstream document references it by ID — it is edited in place like `AccountingSettings` already is, with the audit trail as the change history rather than document-style immutability.

## PERMISSION

`settings.manage` — new, added to `PERMISSIONS` in `src/modules/access/domain/permissions.ts`, default-granted only to `SUPER_ADMIN` and `ADMIN` in `DEFAULT_ROLE_PERMISSIONS`. Gates the entire `/administration/settings` page (read and write together), matching the existing `/accounting/settings` pattern. No other role receives it by default; an authorized `ADMIN` can extend it to another role afterward through the existing roles-permissions UI, exactly as with any other permission.

---

## AUDIT

Every save (`UPDATE` on the singleton row) writes one `AuditEvent`:

- `action: "UPDATE"`
- `entityType: "COMPANY_PROFILE"` (new)
- `entityId: "default"`
- `module: "administration"`
- `beforeSnapshot` / `afterSnapshot`: the changed fields only, matching `updateAccountMappingAction`'s existing shape
- `controlEvent: true` (company identity on legal/commercial documents is a control-relevant change, same tier as an accounting mapping edit)

No reason code is required (this is a routine administrative edit, not a correction/reversal), consistent with how plain settings edits elsewhere in the codebase are audited.

## OUT OF SCOPE

Explicitly and permanently out of Administration Settings' authority — it must never be able to:

- Post, edit, or reverse any inventory movement, valuation entry, or `InventoryValuationBalance` (inventory ledger and valuation stay owned by their own posting engines).
- Create, edit, or resolve any `AccountingAccountMapping`, `PurchaseTaxTreatment`, or `AccountingPeriod` status (all remain owned by `/accounting/settings`, gated by `accounting.manage`).
- Grant, revoke, or default any `PermissionCode` or `Role`/`RolePermission` assignment (owned by `/administration/roles-permissions`, `roles.manage`).
- Edit, delete, or backdate any posted document (`PurchaseOrder`, `GoodsReceipt`, `PurchaseInvoice`, `SalesInvoice`, journals, etc.) or any `AuditEvent`.
- Change production costing method, `ProductionBatchCostSnapshot` values, or `InventoryValuationMethod`.
- Read, display, or accept input for any runtime secret (`DATABASE_URL`, `BETTER_AUTH_SECRET`, bootstrap credentials) or any database/deployment configuration (backup schedule, Windows Task Scheduler, Tailscale, PostgreSQL connection settings).
- Change document numbering prefixes or sequence `nextValue`s (see Risks).

Also out of scope for this design specifically (not because they're forbidden in principle, but because inspection found no existing partial feature or evidenced need to attach a setting to): low-stock alerting, default payment-terms pre-fill, default warehouse pre-fill, session/auth policy tuning, backup retention policy, print-document footer/terms text, and PWA manifest/app metadata.

## RISKS

- **R1 — Numbering/sequence editability was considered and rejected.** An admin occasionally wants to bump a document sequence (e.g., continuing a legacy paper numbering scheme). Making `*Sequence.nextValue` web-editable creates a real audit-integrity risk (duplicate or skipped numbers if edited carelessly) for a need that, in an already-live production system, is better handled as a rare, deliberate, logged one-off DB action at the same rigor as other exceptional operations — not a routine settings-page control. Not recommended for V1.
- **R2 — Retroactive branding on reprints.** Changing the company profile changes how _all_ historical documents reprint from that point forward (present-value rendering, not a point-in-time snapshot). This exactly matches existing, already-accepted behavior for supplier/customer address changes and is not a new risk class this design introduces — but it should be stated plainly to the operator, since "the printed PO from March now shows the new address" could otherwise surprise someone.
- **R3 — Scope creep temptation.** Because `/administration/settings` sounds like a natural home for "anything not yet configurable," there will be ongoing pressure to add more fields later (numbering, backup schedule, session policy, etc.) without a fresh evidenced need each time. This document's boundary list is the guard against that; any future addition should get the same inspect-first treatment this one did, not be added ad hoc.
- **R4 — Minimal but real new attack/change surface.** A new mutable, admin-editable table is still a new mutable, admin-editable table. Kept minimal (six text fields, no relations into any transactional/financial table, no lifecycle) specifically to keep this risk as low as it can be while still closing the real gap.

## DECISIONS REQUIRING APPROVAL

- **D1.** Confirm the scope is **Company / Factory Profile only** (`legalName`, `address`, `city`, `phone`, `email`, `taxRegistrationNo`), text fields, no logo/file upload, not wired into the PWA manifest or root `<title>` in V1. (Recommended: yes.)
- **D2.** Confirm a **new** permission `settings.manage` (default `SUPER_ADMIN`/`ADMIN` only) rather than reusing `roles.manage`, `users.manage`, or `accounting.manage`. (Recommended: yes — none of the existing permissions are a semantic fit, and reusing one would silently grant company-identity edit rights to whoever holds an unrelated permission.)
- **D3.** Confirm print pages and the authenticated shell header read the new setting live (present-value rendering, matching existing supplier/customer address behavior) rather than being frozen per document at creation time. (Recommended: yes — consistent with precedent, and freezing would need a new snapshot mechanism for no evidenced benefit.)
- **D4.** Confirm document numbering prefixes/sequence values remain **not** admin-editable (§Risks R1). (Recommended: yes.)
- **D5.** If the operator would rather not carry even this one narrow setting, the alternative is to **REMOVE** the planned `/administration/settings` sidebar entry entirely and leave the hardcoded `"Hamd Foods ERP"` string as a permanent, non-configurable constant, closing the workflow inventory at 58 `COMPLETE` / 0 `MISSING` instead of implementing this page. This is a legitimate outcome per the task's own instruction ("if no legitimate general settings remain... recommend removing the entry") — but inspection did find one legitimate, evidenced gap, so the default recommendation is D1–D4 (build the narrow page), not removal.

**No implementation, migration, or code change should proceed until D1–D5 are confirmed or amended.**
