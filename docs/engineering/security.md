# Security rules

The trust boundary is browser → application server → data layer → PostgreSQL. The browser must never connect directly to PostgreSQL or receive database credentials.

- Store secrets only in ignored local environment files or a deployment secret store.
- Only variables deliberately prefixed `NEXT_PUBLIC_` may enter browser bundles; Phase 1 defines none.
- Validate mandatory server configuration at startup and fail with actionable, non-secret errors.
- Bind the local database port to `127.0.0.1`, not all network interfaces.
- Apply least privilege to database roles, application permissions, and deployment access.
- Do not return raw database errors, connection strings, or stack traces in user-facing health output.

## Authentication and authorization

- Better Auth owns password hashing, credentials, sessions, and the public authentication protocol. Its mounted handler disables email/password signup.
- Bootstrap and administrator provisioning are server-only. Passwords are never persisted by application use cases, returned to clients, or logged.
- Protected server requests reload user activity and relational role permissions from PostgreSQL. Browser-visible navigation is presentation filtering, never an authorization boundary.
- Every protected page and mutation repeats an active-user/permission check. Deactivation revokes all sessions, and stale inactive sessions are independently rejected.
- Ordinary authorization uses permission codes, not role-name checks. SUPER_ADMIN role-name checks exist only for its explicit preservation invariants.
- Authentication errors remain generic so unknown email, incorrect password, and inactive status are not distinguished to the user.
- `AUTH_BYPASS_ENABLED=true` is a temporary server-only local-development convenience. It resolves a deterministic in-memory development principal through the normal principal boundary and centralized SUPER_ADMIN permission set; it does not disable permission guards, create a database user, trust client input, or enable signup. Environment validation fails closed with `Authentication bypass cannot be enabled in production.` whenever either `APP_ENV` or `NODE_ENV` identifies production. Customer installations must leave it disabled. Before commercial or final UAT, disable the bypass and repeat normal Better Auth login, authorization, logout, and unauthenticated-route checks.

### Account security and recovery

- Authenticated users manage their display name, login email, and password at `/account/security`. Login email remains the sole username model: it is normalized, unique, and confirmed with the current password before change. Password changes require the current password and matching confirmation. Display-name changes never change roles or permissions.
- Better Auth's configured verifier, hasher, credential adapter, and sessions remain authoritative. Successful login-email changes and password changes revoke every session for that user. Administrators require `users.manage` to reset another user's password; only a SUPER_ADMIN may reset a SUPER_ADMIN. Reset never changes the target's roles, permissions, active status, or email and revokes all target sessions.
- The public `/forgot-password` page is guidance only. It never accepts credentials or exposes a reset mutation. Public email/password signup remains disabled. There is no master, universal, or hardcoded recovery password and no remote reset-any-password API.
- Offline recovery exists only as the installed local Windows utility. Its process independently requires an elevated high-integrity Administrator token. It lists only active administrative account display name, login email, roles, and status; password input is hidden and sent to the bundled process only over redirected standard input, never arguments, environment diagnostics, task XML, or logs.
- `PROFILE_UPDATED`, `LOGIN_EMAIL_CHANGED`, `PASSWORD_CHANGED`, `ADMIN_PASSWORD_RESET`, and `LOCAL_ACCOUNT_RECOVERY` are non-secret audit classifications. Audit data may contain the affected identifier and change classification but must never contain a plaintext password, password hash, session token, database URL/password, or Better Auth secret.

### Software licensing

Phase 33 adds offline, signed-license protection for customer installations; see `docs/operations/software-licensing.md` and `docs/specs/phase33-software-protection-design.md` for the full model. The vendor's Ed25519 private signing key never enters this repository, the installer payload, or the running application -- only public verification keys are embedded (`src/server/licensing/public-keys.ts`). License state is authenticated with an HMAC keyed by a value sealed via Windows DPAPI (`LocalMachine` scope), generated locally and never embedded or transmitted -- no hardcoded license secret exists anywhere in the codebase. Restricted mode (an unlicensed or invalid installation) blocks only business mutations; authentication, every read-only page, reports, backups, restore tooling, and account recovery are always available, and no license condition ever encrypts, deletes, or corrupts business data. Licensing enforcement applies only when `APP_ENV=production` on Windows and never activates in development, test, or CI.

### Software updates

Phase 34 adds offline, signed software updates for an already-installed customer installation; see `docs/operations/software-updates.md` and `docs/specs/phase34-secure-update-recovery-design.md` for the full model. Update packages are verified with a second Ed25519 keypair, fully independent of the license-signing keypair (`src/server/updates/update-public-keys.ts`) -- there is no shared type, constant, or code path that could pass one key set where the other is expected. Nothing in a package is extracted until its manifest signature has been verified; every payload path is then validated against the verified manifest (absolute paths, `..` traversal, unexpected/missing/case-colliding entries all rejected) before extraction, and every extracted file is re-hashed against the manifest afterward. `update-state.json` reuses the exact DPAPI/HMAC protection pattern as `license-state.json` (`src/server/shared/protected-json-store.ts`) but with its own dedicated key file, so compromising one never affects the other. The web upload/verify/arm action is enforced only through the ordinary unrestricted `server-guards.ts`, never `licensed-guards.ts` -- a legitimate signed update must remain installable in every license state. The SYSTEM `HamdFoodsERP-Update` Scheduled Task is armed with a controlled `packageId`/`updateId` only, never an arbitrary filesystem path, and independently re-verifies the staged release's integrity before doing anything irreversible.

### Final security hardening

Phase 35 closes a threat-model-driven audit of the complete production ERP; see `docs/specs/phase35-security-hardening-design.md` for the full findings list and reasoning. Fixed:

- **License-restriction consistency**: `src/server/master-data/item-action-handlers.ts` (raw material/finished good/packaging material save and status mutations) now imports `requirePermission` from `licensed-guards` like every other business mutation, closing an undocumented gap where these three item types remained editable in a restricted license state. RBAC itself was never affected -- `inventory.manage` was always required.
- **Information disclosure in server-action failures**: `src/server/shared/action-error.ts`'s `safeActionErrorMessage()` returns a known domain error's own message (e.g. `AccountingPostingError`, `RecipeRepositoryError`, `UpdateServiceError`) but replaces anything else -- including a raw `PrismaClientKnownRequestError`, which satisfies `instanceof Error` exactly like a safe domain error -- with a generic fallback, logging the real error server-side only. Applied to the accounting, recipe, and update-install action catch blocks that previously forwarded `error.message` unconditionally.
- **Dependency currency**: `next` is kept current (patched promptly for disclosed advisories); `pnpm security:audit` (`docs/engineering/testing.md`) and `.github/dependabot.yml` catch future regressions here.
- **Update-signing tool hardening**: `scripts/updates/sign-update-package.ts` invokes PowerShell only via a parameterized script file (`compress-update-package.ps1`) with array-form arguments, never a hand-built `-Command` string -- consistent with every installed script's existing standard.
- **License import ordering**: `src/server/licensing/license-file-store.ts`'s `importLicenseFile` verifies an uploaded `.lic` file's Ed25519 signature before it is ever written to disk, matching the same verify-before-trust ordering Phase 34 already uses for update packages.

Added, all applied via `next.config.ts`'s `headers()`: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` disabling unused browser features, `Strict-Transport-Security` (inert on the mandated loopback-HTTP origin, meaningful on the optional Tailscale HTTPS origin), `Cross-Origin-Opener-Policy: same-origin`, and an **enforced** `Content-Security-Policy`. The CSP needed two relaxations discovered empirically (not guessed) by running Report-Only against the full disposable-DB E2E suite and reading the actual browser violations: `script-src` needs `'unsafe-inline'` because the App Router delivers every page's RSC payload through inline `<script>self.__next_f.push(...)</script>` tags injected by Next's own renderer, and `'unsafe-eval'` because React's development-mode debugging instrumentation calls `eval()` (production React never does); `style-src` needs `'unsafe-inline'` because interactive UI primitives (dropdowns, comboboxes, tooltips) apply computed positioning via inline style at runtime, which CSP checks the same as static markup. Nothing else needed relaxing -- the policy remains `default-src 'self'` with no external script/style/font/image/connect origin permitted anywhere. `images.unoptimized: true` additionally disables the Next.js Image Optimization API (`/_next/image`) entirely, since this app never uses `next/image`.

Rate limiting beyond Better Auth's own production default (100 requests/10s, in-memory, unmodified), 2FA, password-reset delivery, secret rotation, a general-purpose redacting application logger, and automated off-site backup replication remain later-phase or explicitly-deferred work (Phase 35 D4/D5).
